# A2A-antigravityCli 심층 로직 조사 및 KH_Aw 업그레이드 보고서

## 1. 조사 범위

원본 ZIP의 2,519개 파일과 868개 디렉터리를 전수 원장화했습니다. First-party 핵심 영역은 backend 18개, config 3개, shared 4개, tests 11개, frontend 24개, legacy design skill 2개입니다. 모든 파일은 SHA-256과 배포 결정을 가집니다.

원본 Node 소스 전체에 `node --check`를 실행한 결과 문법 실패는 0개였습니다. 원본 테스트는 62개 중 61개 통과, 1개 실패였습니다. 실패 테스트는 로컬 Codex 선택 모델 캐시를 반드시 기대하지만 조사 환경에서는 bundled fallback이 반환되는 환경 의존 문제였습니다.

## 2. 중대 구조 문제와 업그레이드

### F-01. Codex CLI/로컬 세션 결합

원본은 Antigravity/Codex CLI 프로세스, 세션 스트림, 로컬 모델 캐시, 로컬 브라우저 프로필을 중심으로 설계되었습니다. Codex 웹 마켓플레이스 플러그인에서는 이 전제가 맞지 않습니다.

**업그레이드:** 독립 Express/WebSocket 서버를 플러그인 필수 런타임에서 제거했습니다. 스킬과 저장소 내 Python 상태 머신, JSON 계약, 파일 해시, CI로 재구성했습니다. 모델 이름이나 캐시 존재를 완료 조건으로 사용하지 않습니다.

### F-02. 프롬프트 중심 강제의 한계

`config/stages.json`에는 강한 MANDATORY 문구와 방대한 출력 구조가 있지만, 문구 자체는 AI가 생략하거나 형식만 채울 수 있습니다.

**업그레이드:** `kh_aw_cli.py advance`가 실제 파일과 필드, 개수, 경로, PNG 헤더/크기, SHA-256, 테스트 로그를 직접 판정합니다. 설명 문장만으로는 단계가 전환되지 않습니다.

### F-03. 실패 시 파이프라인 정지 또는 복잡한 재개 위험

원본은 큰 `pipeline.mjs`와 `auto-repair.mjs`에 재시도·세션·체크포인트·stale repair 처리가 집중되어 있습니다. 장점은 많지만 웹 플러그인에 불필요한 상태가 많고, 오래된 성공/실패 보고서 수렴 문제가 복잡합니다.

**업그레이드:** 게이트 실패는 프로세스 종료코드 0과 `repair-required-nonterminal` 상태를 반환하여 상위 오케스트레이션을 멈추지 않습니다. 동시에 단계는 통과하지 않습니다. 동일 실패 서명은 3회 후 전략 세대를 증가시켜 문구 변경이 아닌 다른 수리 메커니즘을 요구합니다.

### F-04. 분석폴더와 결과물 경계

원본에는 변경 검사와 경로 보호가 있으나, 사후 검출 이전에 원본이 변경될 가능성과 분석폴더=프로젝트 루트인 경계가 남습니다.

**업그레이드:** 분석폴더가 제공되면 전체 파일 ZIP 백업과 SHA-256 스냅샷을 먼저 만들고, 결과물 경로가 분석폴더 내부이면 초기화 자체를 거부합니다. 변조가 발견되면 백업에서 자동 복구하고 재검증합니다. 분석폴더가 없을 때는 별도 self-analysis 모드로 기록합니다.

### F-05. 웹 검색과 실제 본문 증거의 차이

원본 `web-research.mjs`는 페이지를 fetch하고 excerpt를 만들지만 source registry는 원문 전체 파일과 해시보다 excerpt 중심입니다. DuckDuckGo HTML 파싱과 GitHub API 응답 구조에도 결합됩니다. 검색 성공·본문 적용·라이선스 적용의 경계가 약해질 수 있습니다.

**업그레이드:** 검색과 증거 등록을 분리했습니다. Codex 웹 도구 또는 선택적 fetch가 실제 HTML/README 본문 파일을 저장하고, `register-source`가 원문/추출문 경로, SHA-256, 바이트 수, 추출 문자 수, HTTP 상태, 정확한 URL, 프로젝트 적합 이유, 라이선스 메모를 등록합니다. 검색 엔진 결과 페이지는 최종 출처로 거부됩니다.

### F-06. 수동 컨셉·색상 선택 잔존

원본 frontend와 stage prompt에 concept picker, color picker, selected colors, selected concepts가 존재합니다. 이는 사용자가 요구한 향후 작업 시 자동 연구 방식과 충돌합니다.

**업그레이드:** 해당 UI 파일은 마켓플레이스 런타임에서 제거했습니다. 모든 계약에서 관련 키를 금지하며 자동수리가 발견 즉시 제거합니다. 디자인 출처 모드는 `dynamic-web-body-research` 또는 기존 브랜드를 함께 쓰는 동적 모드만 허용합니다.

### F-07. 고정 디자인 처방

legacy taste skill은 특정 폰트, AIDA, GSAP, Picsum, hero 구조와 랜덤 선택을 광범위하게 고정합니다. 랜딩 페이지에는 도움이 될 수 있으나 업무 앱, 폼, 지도, 관리 화면과 프로젝트 고유 브랜드에는 부적합할 수 있습니다.

**업그레이드:** KH_Aw 자체에는 생성 프로젝트의 컨셉·팔레트·폰트·사이트를 하드코딩하지 않습니다. 매 실행의 요구사항에서 연구 계획을 만들고 실제 본문 출처를 페이지별 장부에 연결합니다. 고품질 이미지를 요구하지만 목적·권리·배치가 없는 장식 이미지는 통과하지 않습니다.

### F-08. 샘플 목업으로 전체 설계를 대체할 위험

원본에는 1:1 page gate 테스트가 있어 좋은 기반입니다. 그러나 최종 사용자 요구는 “샘플 몇 개” 금지를 더 명시적으로 요구합니다.

**업그레이드:** page inventory와 design ledger의 ID 집합과 개수를 정확히 비교하고, 각 페이지의 mockupPath와 screenshotPath가 모두 고유한지 확인합니다. 각 PNG는 실제 PNG 헤더와 최소 320x568 크기를 가져야 하며 전체 페이지 보드도 별도 필요합니다.

### F-09. 이미지·모션 계획과 실제 코드 사이의 증거

계획 장부만 풍부하고 실제 파일에서 사용되지 않는 자산/모션이 남을 수 있습니다.

**업그레이드:** 구현 게이트가 이미지 파일 존재·크기·출처 또는 생성 프롬프트·권리·usageLocations를 검사합니다. 모션은 targetFile 안의 implementationMarker와 reducedMotionMarker가 실제로 존재해야 합니다. 디자인에서 required인 이미지/모션 ID는 페이지 구현 장부에 연결되어야 합니다.

### F-10. 공개 ZIP 오염과 보안

원본의 약 58.15 MiB가 `.playwright-cli`이며, `data`, `output`, `scratch`, 로그, 백업, `node_modules`, `.git`이 함께 포함되어 있습니다. 데이터베이스와 브라우저 프로필은 공개 배포에 부적합합니다.

**업그레이드:** 마켓플레이스 패키지는 재작성된 소스·문서·테스트·브랜딩 자산만 포함합니다. 2,519개 원본 파일은 원장에 남기되 민감/생성 항목을 GitHub에 복사하지 않습니다.

## 3. 추가 개선 사항

1. 원자적 JSON 저장으로 중간 쓰기 손상을 줄였습니다.
2. 경로가 run root/plugin root를 벗어나지 않는지 검사합니다.
3. strict CI 모드와 비종료 작업 모드를 분리했습니다.
4. 공개 마켓플레이스 승인과 GitHub 배포를 구분합니다.
5. 앱과 웹 target pipeline을 분리합니다.
6. 모든 요구사항 ID를 분석 및 연구 요소에 연결하도록 강제합니다.
7. 모든 페이지에 이미지/모션 사용 여부와 구체적 이유를 요구합니다.
8. 단일 페이지가 아닌 경우 최소 3분의 1 이상의 페이지에서 의미 있는 이미지와 모션을 요구합니다.
9. 접근성을 위해 reduced-motion 실코드 증거를 요구합니다.
10. 테스트 명령은 종료코드와 로그 파일로 남깁니다.

## 4. 플랫폼 한계

스킬 전용 플러그인은 Codex 자체를 수정하는 커널 훅이 아닙니다. 사용자가 플러그인을 전혀 선택하지 않거나 모델이 실행 파일을 한 번도 호출하지 않는 상황까지 외부 코드가 강제로 차단할 수는 없습니다. KH_Aw는 플러그인이 호출된 이후 사용할 수 있는 가장 강한 방식—상태 머신, 물리 증거, SHA-256, 불변 스냅샷, 게이트, CI—을 적용합니다. 공개 Plugin Directory 등록은 GitHub push와 별도의 OpenAI 검토 절차입니다.
