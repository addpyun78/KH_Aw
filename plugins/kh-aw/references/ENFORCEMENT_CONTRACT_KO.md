# KH_Aw 실행 강제 계약

## 1. 목적

KH_Aw는 앱·웹 회사가 실제 프로젝트를 분석하고, 웹 본문 및 GitHub 본문을 직접 추출하여 근거를 만들고, 전체 페이지의 시각 목업을 먼저 완성한 다음 실제 코드·이미지·모션·로직을 구현하고, 검증 실패가 발생하면 자동수리 후 원래 흐름으로 복귀하도록 만드는 Codex 플러그인이다.

이 계약은 프롬프트 문구만으로 완료를 인정하지 않는다. 단계 완료 여부는 `scripts/kh_aw.py`가 물리 파일, 해시, 페이지·필드·로직·기능의 일대일 원장, 실제 실행 결과, 화면별 렌더 이미지와 테스트 증거를 검사하여 결정한다.

## 2. 분석폴더 분기

### 2.1 사용자가 분석폴더를 제공한 경우

1. `analysisMode`는 `provided`로 고정한다.
2. 분석폴더는 읽기 전용 원본이다.
3. 부트스트랩 시 전체 파일 해시 원장과 source-shadow를 만든다.
4. 결과물은 분석폴더 밖의 별도 `implementationRoot`에 생성한다.
5. 분석폴더가 수정되면 다음 게이트에서 즉시 탐지한다.
6. 자동수리는 source-shadow에서 원본을 복구하고 추가 파일을 제거한 후 다시 검증한다.
7. 분석 결과에는 파일 단위 근거가 반드시 있어야 한다.

### 2.2 사용자가 분석폴더를 제공하지 않은 경우

1. `analysisMode`는 `not-provided`로 고정한다.
2. 현재 프로젝트를 분석 및 구현 대상으로 사용한다.
3. `.kh_aw/`는 증거·상태·수리 티켓 전용 작업공간으로 분리한다.
4. `.kh_aw`, `.git`, `node_modules`, 빌드 캐시는 프로젝트 분석 원장에서 제외한다.
5. 실제 구현 파일은 현재 프로젝트에 생성·수정할 수 있다.

두 경로는 같은 프롬프트 변형이 아니라 코드가 먼저 분기하고 서로 다른 출력·보호 규칙을 적용한다.

## 3. 단계 상태기계

고정 단계는 다음과 같다.

1. `intake`: 원문 지시 줄 보존, 요구사항 ID 연결
2. `analyze`: 파일·페이지·필드·로직·기능 전수 분석
3. `research`: 웹 및 GitHub 본문 직접 추출
4. `design`: 전체 페이지 시각 목업과 구현 설계
5. `implement`: 실제 코드·이미지·모션·데이터·로직 구현
6. `review`: 화면별 실제 렌더 비교와 기능·디자인 검토
7. `test`: 빌드·테스트·접근성·시각 회귀 검증
8. `release`: 보안·누락·원본 보존·전체 증거 최종 검증

단계가 실패하면 상태는 `failed`나 `stopped`가 아니라 `repairing`이 된다. 모든 실패는 수리 가능한 작업으로 분류하며 `terminalState`를 만들지 않는다.

## 4. 자동수리 루프

모든 게이트는 같은 수리 흐름을 사용한다.

1. 검증기가 실패 항목을 코드와 파일 경로로 출력한다.
2. `tickets/REPAIR-<STAGE>-<ATTEMPT>.json`을 생성한다.
3. 결정론 수리는 즉시 실행한다.
   - 누락 디렉터리 생성
   - 깨진 JSON의 last-good 복구
   - 분석 원본 변조 복구
   - 누락·중복 추적 ID 정상화
   - 단계별 비통과 scaffold 생성
4. 의미 수리가 필요한 항목은 `aiRepairActions`로 남긴다.
5. Codex는 티켓의 모든 항목을 실제 파일로 수리한다.
6. 같은 검증기를 다시 실행한다.
7. 같은 문제가 반복되면 이전과 다른 수리 전략과 회귀 검사를 추가한다.
8. 통과하면 열린 티켓을 검증 증거로 닫고 다음 단계로 자동 진행한다.

티켓의 문장을 수정하거나 `passed: true`를 직접 쓰는 행위는 수리가 아니다. 원인 파일·목업·본문 추출·코드·스크린샷·테스트 실행을 실제로 만들어야 한다.

## 5. 원문 누락 방지

1. 사용자 지시의 의미 있는 모든 줄을 `raw-instruction-ledger.json`에 원문 그대로 보존한다.
2. 각 줄은 하나 이상의 `REQ-*` 요구사항 ID와 연결한다.
3. 모든 요구사항은 분석, 연구, 설계, 구현, 검토, 테스트 원장에 같은 ID로 유지한다.
4. 줄이 요구사항에 연결되지 않거나 존재하지 않는 ID에 연결되면 intake가 실패한다.
5. 요약 문서는 보조 자료일 뿐 원문 원장을 대체하지 못한다.

## 6. 웹 본문 직접 추출

1. 검색 결과 URL만 기록하는 것은 금지한다.
2. `research_extract.py` 또는 브라우저 도구로 본문을 직접 연다.
3. HTTP 200, 본문 길이, 본문 SHA-256, 실제 본문 발췌, 제목, 헤딩, 추출 방식을 기록한다.
4. CAPTCHA, access denied, JavaScript 안내만 나온 페이지는 거절한다.
5. GitHub는 README·공식 문서·소스 파일 본문을 직접 추출한다.
6. 각 연구 요소는 기본적으로 웹 본문 2건과 GitHub 본문 2건을 요구한다.
7. 주소검색의 지정 예외 코드만 각각 1건을 허용한다.
8. 경쟁 기능을 채택하면 `featureId`를 만들고 화면·영역·로직·파일·검증까지 일대일로 추적한다.
9. 연구 근거의 색상·타이포·레이아웃·이미지·아이콘·모션은 그대로 복사하지 않고 프로젝트 목적에 맞게 판단하고 출처를 남긴다.

## 7. 수동 컨셉·색상 선택 제거

1. KH_Aw에는 특정 컨셉, 특정 팔레트, 특정 템플릿, 특정 사이트를 하드코딩하지 않는다.
2. 사용자에게 컨셉 목록이나 색상 선택 팝업을 먼저 보여 주는 흐름을 사용하지 않는다.
3. 프로젝트 실행 시점에 AI가 프로젝트 요구사항에서 연구 질의를 동적으로 만든다.
4. 실제 본문 근거와 브랜드 목적을 바탕으로 디자인 토큰을 결정한다.
5. 모든 토큰은 `designTokenProvenance`에 결정 이유와 sourceEvidenceId를 기록한다.
6. `manualConcept`, `selectedConcept`, `selectedColors`, `colorPicker` 등 수동 선택 키가 설계 산출물에 존재하면 설계 게이트가 실패한다.
7. 사용자가 명시적으로 기존 브랜드 가이드나 색상을 요구한 경우 그것은 수동 선택 UI가 아니라 사용자 요구사항 근거로 취급하고 원장에 기록한다.

## 8. 전체 페이지 시각 목업 선행

1. 샘플 몇 개, 대표 화면, 텍스트 와이어프레임으로 설계를 통과할 수 없다.
2. 분석의 `pageInventory`와 설계의 `pageInventory`는 ID와 순서가 완전히 일치해야 한다.
3. 모든 pageId는 고유한 HTML 또는 SVG 시각 목업 파일 하나와 연결한다.
4. 같은 목업 파일을 여러 페이지가 공유하면 실패한다.
5. 목업은 헤더·내비게이션·본문·폼·버튼·이미지·상태·반응형 배치를 실제 시각 구조로 포함해야 한다.
6. scaffold 표시가 남은 파일은 목업으로 인정하지 않는다.
7. 전체 페이지를 한눈에 비교하는 visualStructureBoard도 물리 HTML로 만든다.
8. 모든 목업이 통과하기 전에는 구현 단계로 넘어가지 않는다.
9. 구현은 목업의 영역·필드·로직·기능·이미지·모션을 일대일로 연결한다.

## 9. 소기업용 고품질 시각 정책

1. 대기업식 최소 필요 기능만 배치한 정적 화면을 기본값으로 사용하지 않는다.
2. 공개 사용자 화면마다 프로젝트 목적에 맞는 의미 있는 이미지·일러스트·사진·도표 중 하나 이상을 계획한다.
3. 공개 사용자 화면마다 정보 위계, 피드백, 탐색 또는 브랜드 경험을 개선하는 목적성 모션을 계획한다.
4. 모션은 trigger, 시작·종료 상태, duration, easing, purpose, reduced-motion fallback을 기록한다.
5. 이미지에는 목적, 비율, 출처 또는 생성 프롬프트, 라이선스, 대체 수단을 기록한다.
6. 설정·법률·보안 화면처럼 이미지·모션이 오히려 방해되는 경우 `engagementException`에 프로젝트별 이유를 기록할 수 있다.
7. 단순 장식, 과도한 애니메이션, 성능 저하, 접근성 침해는 고품질로 인정하지 않는다.
8. 실제 구현 파일에 이미지가 바인딩되고 모션 코드 및 reduced-motion 코드가 있어야 한다.
9. 실제 런타임 화면에서 확인되지 않은 계획은 구현 완료로 인정하지 않는다.

## 10. 구현 일대일 추적

다음 축은 하나라도 누락되면 구현 게이트가 실패한다.

- pageId: 분석 → 설계 목업 → 구현 파일 → 리뷰 → 테스트 → 스크린샷
- fieldId: 분석 필드 → 화면 위치 → 데이터 경로 → 검증·권한 → 구현 → 테스트
- logicId: 트리거 → 입력 → 처리 → 출력 → 오류·빈값·로딩 → 코드 → 테스트
- featureId: 연구 본문 → 개선안 → 화면 위치 → 코드 → 런타임 검증
- imageId: 이미지 슬롯 → 자산 파일 → 사용 위치 → 출처·라이선스 → 런타임 검증
- motionId: 모션 스토리보드 → 코드 위치 → reduced-motion → 런타임 검증

## 11. 리뷰 및 테스트

1. 모든 페이지에 실제 PNG 런타임 스크린샷을 만든다.
2. 최소 크기와 파일 크기를 검사하여 빈 파일·1픽셀·가짜 증거를 거절한다.
3. 목업과 구현 화면을 구조, 필드, 로직, 기능, 이미지, 모션, 겹침 여부로 비교한다.
4. 페이지 하나라도 실패하면 해당 소유 단계로 자동수리 티켓을 돌려보낸다.
5. 실제 빌드·테스트 명령, exit code 0, 출력 SHA-256을 기록한다.
6. 모든 페이지의 시각 회귀와 접근성 검사를 포함한다.
7. 오류를 숨기거나 테스트를 삭제하여 통과시키는 것을 금지한다.

## 12. 보안 및 공개 배포

1. 쿠키, Login Data, 브라우저 프로필, SQLite 세션 DB, `.env`, 실제 토큰·비밀번호를 공개 저장소에 포함하지 않는다.
2. `node_modules`, 빌드 캐시, 로그, scratch, 실행 결과, 개인 프로젝트 데이터, Git 메타데이터를 플러그인에 포함하지 않는다.
3. `.gitignore`와 보안 스캐너로 재유입을 차단한다.
4. 분석 원본 전체 전수 원장은 보고서에 남기되 위험 파일 자체는 배포하지 않는다.
5. 라이선스가 불명확한 이미지·폰트·아이콘은 다운로드·재배포하지 않는다.
6. 출처와 라이선스를 증거 원장에 남기며 사용할 수 없으면 다른 출처를 자동 연구한다.

## 13. 회사 운영과 비용 정책

1. 무료·오픈소스·현재 보유한 도구를 우선한다.
2. 유료 API나 서비스는 사용자가 승인하지 않으면 구현 필수 의존성으로 넣지 않는다.
3. 제품별 비용 원장, 배포 비용, 외부 서비스 대체 수단을 기록한다.
4. 판매 가능한 품질을 위해 기능, 전환, 온보딩, 신뢰, 분석, 유지보수, 접근성, 성능, 보안을 함께 검증한다.
5. 단순 데모나 목업 APK·단일 HTML을 완제품으로 보고하지 않는다.

## 14. 완료 정의

완료는 다음 조건을 모두 충족할 때만 성립한다.

- 8개 단계가 같은 상태 파일에서 모두 `passed`
- 열린 수리 티켓 0건
- `release/release-receipt.json` 존재
- 사용자 분석폴더 원본 해시 일치
- 요구사항·페이지·필드·로직·기능·이미지·모션 누락 0건
- 실제 코드·빌드·테스트·스크린샷·접근성 증거 존재
- 공개 배포 보안 검사 통과

AI의 “완료했습니다”라는 문장은 완료 증거가 아니다.
